The core workflow

Technical detail

Two review boundaries for ROADMAP: challenge the frozen plan before build, then compare the completed implementation with that plan before DONE. A separate agent chat or human performs the judgment; Overseer provides the structure and durable record.

Mechanical check — the frozen plan against on-disk evidence

Define what “done” means before the build: scope, phases, deliverables, files, test exits, or project-owned checks. Review that plan independently, then compare the completed work with the accepted freeze instead of trusting the builder’s summary.

Review before build

  • Freeze the plan — write the intended outcome, phases, outputs, and acceptance evidence in ROADMAP before implementation starts.
  • Challenge it independently — give the freeze to a separate agent chat or human reviewer with no incentive to approve it.
  • Loop on findings — revise and re-review until the plan is clear enough to build without guesswork.

Roadmap · Handover · Phases

  • ROADMAP — the phase board: what is planned, frozen, building, under review, or done.
  • HANDOVER — the session baton: what landed, what remains true, and what the next session should do.
  • Phases — turn an accepted plan into bounded slices with explicit outputs and checks.
  • Continuity — the current CLI binds NEXT to the repository and revision so the right work reaches the right session.

The failure mode

Why governance honesty matters

AI-assisted work breaks down at the boundaries between planning, building, review, and the next session.

  • Amnesia

    Each new chat re-derives context from scratch.

  • Self-approval

    The same builder declares its own plan or implementation complete.

  • Silent drift

    A handoff outlives the branch or revision that produced it.

  • Skipped checkpoints

    A plausible summary replaces evidence and expensive mistakes surface late.

Overseer Kit makes shortcuts visible before work advances — by keeping the plan, reviews, phase state, evidence, and next handoff explicit.

The loop

How it works

Lock the plan, challenge it independently, build accepted phases, then verify the implementation before DONE.

  1. 01

    Lock and challenge the plan

    Write what will be built, how it will be phased, and what evidence will count. Freeze it, then have a separate agent chat or human reviewer try to find gaps.

  2. 02

    Build in bounded phases

    Implement only the accepted scope. Each phase carries declared outputs and project-owned checks so later sessions do not have to reconstruct intent.

  3. 03

    Review the completed build

    Compare the implementation and its evidence with the frozen plan. Resolve findings and re-check before marking the phase complete.

  4. 04

    Hand over the truth

    Update ROADMAP and HANDOVER to match what actually landed. The rc.1 CLI then keeps the next task bound to the correct repository and revision.

Get started

This site is informational and does not run Overseer. Install the reviewed prerelease, initialize an authorized repository, then use the governance loop with the agent tools and reviewers you already trust.

Path 1 — Install and initialize start here

  1. Follow the reviewed v1.0.0-rc.1 INSTALL-AND-ROLLBACK.md guide.
  2. Set PROJECT_ROOT to an existing Git checkout you are authorized to initialize.
  3. Run ./cli/ok with init --vcs git and the required repository name and context. Existing ROADMAP and HANDOVER files are preserved.
  4. Use the repository-bound launcher to inspect status and carry the reviewed next task between sessions.

Git-only is a complete ongoing mode. The governance workflow does not require Muse, a hosted service, or a new agent product.

Path 2 — Freeze and review the plan

  1. Write the goal, scope, phases, outputs, and acceptance evidence in ROADMAP.
  2. Freeze the plan with the governance loop, then give it to a separate agent chat or human reviewer.
  3. Resolve cited findings and re-review until the plan is safe to treat as build input.
  4. Record the accepted state so later phases do not silently reinterpret it.

Path 3 — Build, verify, and hand over

  1. Build only the accepted phases and run project checks; then have a separate reviewer compare the implementation and evidence with the frozen plan.
  2. After findings clear, update ROADMAP and HANDOVER together and publish the next reviewed task.

Overseer supplies the rails and durable state. It does not run agents, appoint the independent reviewer, decide that work is good, or merge code.
